# Visit attribution — how the evidence works

Site: https://evanston-senior-care-guide.netlify.app
Netlify project: `evanston-senior-care-guide` (`e25a95a5-7a87-4d1c-bae7-8c35d496dded`)

## The standard this is built to

If Jane Smith submits on 8 October and walks into Westminster Place on
12 October, there has to be credible evidence that Jane Smith existed as a
prospect generated by this site on the 8th — created *before* Westminster
received her, and not something that could have been typed up afterwards.

Two things make that credible, and the design turns on the difference:

| | where it comes from | can it be edited after the fact |
|---|---|---|
| Submission ID | `crypto.randomUUID()` inside the function | no — generated server-side, returned to the visitor on screen |
| Timestamp | the server clock, `new Date().toISOString()` | no — the browser never supplies it and the function ignores it if sent |
| Retained record | Netlify Blobs, site-scoped store `visit-attribution` | it is a stored object, separate from any mailbox |
| Email notification | sent by the provider, from their servers | the email is a *copy*; the record is the original |

The email alone would be weak evidence, because an email in your own mailbox
is something you could have written. That is exactly why the stored record
exists and is written **first**: the function saves and re-reads the record
before it sends anything, and refuses to report success if the save failed.

## The chain, end to end

1. Visitor completes the six-question assessment. Answers never leave the
   browser.
2. Result shows a care level. Westminster Place appears below it as a
   disclosed local option.
3. Visitor fills in the "Planning to visit Westminster Place?" form:
   first name, last name, email, phone (optional), planned visit date, and
   an explicit consent checkbox.
4. `POST /api/plan-visit` validates it, generates the submission ID and the
   server timestamp, writes the record, **reads the record back** to confirm
   it is really there, then sends the email.
5. Visitor sees "Visit saved.", the reference ID, and the three ways to reach
   Westminster. They are told plainly that nothing was scheduled.
6. Visitor walks into Westminster normally. Nothing to show, nothing to
   mention, no coworker involved.
7. Westminster records them through its own intake.
8. You match the name against your record, which pre-dates their arrival.

## What you need to set (two values)

Both are Netlify environment variables on this project:
**Project configuration → Environment variables**. Neither ever reaches the
browser — the functions read them server-side only.

### 1. `PLAN_VISIT_FORM_KEY` — turns the email on

A Web3Forms access key. The key itself determines the destination address,
which is why no email address appears anywhere in this repository.

- Go to https://web3forms.com
- Enter the address you want notifications sent to
- They email you an access key — paste that as the value

Until this is set, submissions are **still recorded** and the response
reports `"notification": "not_configured"`. It never pretends to have sent
an email it did not send.

Email format once live:

```
Subject: New Westminster Visit Lead — Evanston Senior Care Guide

New prospective Westminster Place walk-in generated through the
Evanston Senior Care Guide.

Name: Jane Smith
Email: jane@example.com
Phone: (847) 555-0134
Planned visit: 2026-10-12
Submission ID: 56670960-6a74-4995-9953-ade7f830e2c4
Submitted: 2026-10-08T15:47:53.854Z
Source: Evanston Senior Care Guide
```

No assessment answers. No care level. No health information. There is
nothing of that kind in scope at that point in the code.

### 2. `PLAN_VISIT_EXPORT_TOKEN` — lets you read the records back

Any long random string. Generate one with:

```
node -e "console.log(require('crypto').randomBytes(24).toString('hex'))"
```

Then read the file whenever you need it:

```
# JSON, oldest first
curl -H "Authorization: Bearer <your-token>" \
  https://evanston-senior-care-guide.netlify.app/api/plan-visit-export

# spreadsheet
curl -H "Authorization: Bearer <your-token>" \
  "https://evanston-senior-care-guide.netlify.app/api/plan-visit-export?format=csv" \
  -o westminster-visit-leads.csv
```

Until this is set the export **refuses every request** — that is the correct
default for a file of names and phone numbers. There is no query-string key
fallback and no partial-access mode.

Removing one record (a test row, a mistake, or someone who asks to be
removed):

```
curl -X DELETE -H "Authorization: Bearer <your-token>" \
  "https://evanston-senior-care-guide.netlify.app/api/plan-visit-export?id=<submissionId>"
```

## What the endpoint refuses

Verified live on 2026-10-08 against the production URL:

| request | answer |
|---|---|
| valid submission | `200` + submission ID + server timestamp |
| phone only, no email | `200` — one contact method is enough |
| neither email nor phone | `400` "Add an email address or a phone number" |
| consent box unticked | `400` "Please confirm you understand what this form does" |
| a health or quiz field in the payload | `422` "refuses health and assessment data. Nothing was stored." |
| a field that is not one of the six | `422` "Unexpected fields. Nothing was stored." |
| a date in the past | `400` "That date has already passed" |
| `GET` | `405` "Use POST." |
| export without a token | `503` / `401` |
| the record fails to save | `503` — and it says nothing was stored |

## Guardrails that are enforced in code, not just promised

- `assessment.js` cannot contain the word "Westminster" or "Presbyterian".
  The build fails if it ever does. The assessment returns a **care level**
  and nothing else.
- The identifiable submission and the assessment are never joined. The
  browser builds the payload field by field from the form, never from the
  answers object, and the server refuses the request outright if an
  assessment or health field appears in it.
- No secret is readable from the browser. Asserted by the test suite against
  `app.js` and `index.html`.
- Nothing is transmitted to Westminster. Asserted: the function makes no
  request to any Westminster host.
- No claim is made about Westminster's hours, walk-in policy, appointment
  availability, pricing, parking or procedures. Only three facts appear
  anywhere: the address, the phone number and the official website.

The browser suite drives real headless Edge: it types into the form, presses
the button, and reads the live endpoint's answer off the wire. Each run
creates one real record named "Browser Harness <width>". Delete those with
the DELETE call above once the export token is set.

## Deploying

```
npx netlify deploy --prod --dir=_dist --functions=netlify/functions \
  --skip-functions-cache --site=e25a95a5-7a87-4d1c-bae7-8c35d496dded
```

`_dist` holds only what a visitor can reach. Harnesses and screenshots stay
out of it deliberately.

One thing worth knowing: a `[[redirects]]` rule pointing `/api/plan-visit` at
`/.netlify/functions/plan-visit` **shadows** the function and makes it 404.
The function declares its own path via `export const config = { path }`.
Do not add a redirect for it.
